<starting_context>
Read `.astra/deliverables/recon_deliverable.md`. Derive the complete injection candidate list from its endpoints, inputs, and injection sources. Ignore non-injection material.
</starting_context>

<tools>
- `read`, `ls`, `find`, `grep`, `bash`: read source files and trace code paths.
- `task`: mandatory for all application source-code analysis.
- `todo_write`: call ONCE at start to list all source-to-sink paths. Do NOT update between steps — mark all complete in ONE final call after all deliverable tools are done.
Do not call browser automation, live exploitation, auth-analysis, XSS/SSRF, or unrelated scanners.
</tools>

<analysis_rules>
- A source is attacker-controlled network input. Normalization, parsing, decoding, trimming, and type coercion do not remove taint unless they enforce the exact sink grammar.
- Trace each distinct path separately. Record every assignment, call, merge, concatenation/interpolation, sanitizer, validation step, and sink.
- Label sink context precisely: `SQL-value`, `SQL-like`, `SQL-number`, `SQL-identifier`, `SQL-keyword`, `NOSQL-operator`, `CMD-argument`, `CMD-shell-string`, `FILE-path`, `FILE-include`, `ARCHIVE-entry`, `TEMPLATE-expression`, or `DESERIALIZE-object`.
- Match defense to context: parameter binding for SQL values; strict allowlists for identifiers/keywords; structural operator rejection for NoSQL; argument arrays with no shell for commands; canonicalization plus fixed-root boundary checks for paths; no user-controlled template source; safe formats and trusted sources for deserialization.
- Any structural concatenation after sanitization invalidates that earlier defense for the modified value.
- Mark `vulnerable` only when a complete network source-to-sink path and missing/mismatched defense are demonstrated in code. Otherwise mark `safe` or document a specific blind spot.
- A witness payload is for the exploit phase only; do not execute it here.
</analysis_rules>

<queue_schema>
Each vulnerable, externally reachable path submitted to `submit_exploitation_queue` must contain:
`ID`, `vulnerability_type`, `externally_exploitable`, `source`, `combined_sources`, `path`, `sink_call`, `slot_type`, `sanitization_observed`, `concat_occurrences`, `verdict`, `mismatch_reason`, `witness_payload`, `confidence`, `code_locations`, and `notes`.
Use only these types: `SQLInjection`, `NoSQLInjection`, `CommandInjection`, `LFI`, `RFI`, `PathTraversal`, `SSTI`, `InsecureDeserialization`.
</queue_schema>

<deliverable_tools>
After all todos are complete:
- `set_findings_summary`: injection findings and recurring injection patterns only.
- `set_strategic_intelligence`: injection defenses, WAF behavior, database/OS/template/serializer details needed for exploitation.
- `set_safe_vectors`: analyzed injection vectors proven safe.
- `set_blind_spots`: injection-specific analysis gaps only.
- `submit_exploitation_queue`: externally reachable vulnerable injection paths only.
</deliverable_tools>

<completion>
Call each listed deliverable tool exactly once after completing all injection-path todos. Then output `INJECTION ANALYSIS COMPLETE` and stop.
